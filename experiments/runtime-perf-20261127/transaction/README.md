# 事务快照：独立性能实验

结论：**NO-GO，不将快照微优化集成进产品。** 当前成功出牌没有重复完整快照：Run 只抓取一次完整 Run 图，Combat 接收一次性的同目标能力。保留现有事务覆盖和嵌套失败时的原地复原。历史 SDK P95 8.54 ms 是 120 帧的稳态 Step，不是提交延迟；本实验是另一运行时与测量边界。

## 固定输入与复验

- develop commit 32a15219aecd145c59cb1b2fcf477e5556766e5d，tree 1256fecdf9ae57019d65a77bb4733cbaa00cf3c6。先按仓库流程安装 Node 24 / npm 依赖并校验 LFS 对象。实验生成器、脚本和结果均独立；不覆盖产品 Lua 和发版工件。
- 在该 checkout 根目录执行 bash <path-to-this-deliverable>/repro/replay.sh。默认 Host pin CPU 6；快照微测 CPU 7；可用 TX_CPU 和 TX_MICRO_CPU 选择允许 CPU。使用 768 MiB 堆上限，不是 768 MiB RSS/设备限制。
- 复用 scripts/runtime-baseline/production-inputs.mjs 生成当前正式配置 UI、原生模板和艺术绑定，及 tests/lua/support/production_performance.lua 的真实入口和操作。与仓库种子 42 基准不同：固定种子 10 自然遇到 2 Louse，保留原基准的 75 张牌构造压力、手牌 10 张、第一敌人 300 HP 的连续出牌控制设置；这不是自然游玩。
- 各独立 Node 进程暖机 30 更新，量其后 120 次更新和三次出牌。A/B、B/A、A/B 串行按同机同 CPU 重启。A 完全维持原实现，B 直接检查键的类型、不在每次抓取建类型缓存；图遍历和两条 rawset 回滚循环不变。主计时不装 require、原生控件调用或 Lua 层函数观察器，仅在 Host 输入/Update 边界采时。report.json 包含样本；观察组不并入主计时。
- 提交由 Host Click 接收器触发，Down/Up/Click 分开计时，历史 SDK 则在 Up 提交；不可直接计算两者涨跌。未测 GPU、屏幕可见反馈、实际系统/手机耗时，也没有候选正式 GIL。

## 分段归因（单独 observer）

3 次提交各抓 1 份完整快照，共 3 次。Run.play 层包含快照和 Combat.play，不能叠加。提交 Click 墙钟：548.855 / 255.596 / 394.949 ms。

| 阶段 | 三次样本 ms |
| --- | --- |
| Run.play 全部，含快照、Combat 和提交 | 262.168 / 98.713 / 132.968 |
| 完整快照抓取 | 252.308 / 94.048 / 124.433 |
| Combat.play，含已有的一次性回滚所有者消费 | 8.453 / 3.808 / 7.156 |
| 每次提交同步前置 render + 首个反馈帧 render | 67.848 + 205.544 / 66.847 + 68.929 / 91.037 + 159.759 |
| 后续动画 | 另列 feedbackUpdate；观察组的 render/refresh 可嵌套，未从前台耗时推断 GPU |

观察组 3 个提交之间（含选牌、提交和整个反馈周期）有 68,602 次 Host 控件方法调用和 84,139 次属性写入（包括查询；不等于真正引擎调用）。当前 abyss_battle_actions.lua::perform 先写过去状态并调用 protected render、再调用 Run.play，再由 feedback:begin 绘制首帧。playSelected 在正式配置且已绘制首帧时复用之，不再额外做曾有的独立后置刷新；不能把“同步两次 render”写成“会做三次”。前置呈现失败时会拒绝尚未执行的出牌，发布前核心失败以原地回滚。

## 原子性防回退

基线和直接检查方案均通过原图等价（96 组稀疏、共享、循环、仅键可达等检查及 20,000 层深图）、键类型、9 组回滚所有者、5 组真实出牌事务测试。原注册故障注入覆盖伤害后抛非字符串错误、奖励后拒绝/抛错，检查旧事件帧、catalog、数据、引用和重试不重复提交。删掉仅键可达图遍历的本地负控因 “snapshot target is not captured” 失败。未把这个必须复原的图缩成可变字段白名单。
## 实测 A/B

| 指标 | A 现行 | B 不缓存键类型 |
| --- | ---: | ---: |
| 提交 Click P50 / P95，ms（9 次/组） | **171.236 / 347.251** | **168.736 / 302.573** |
| 稳态 Update P50 / P95，ms（360 帧/组） | 2.910 / 5.827 | 2.947 / 5.830 |
| 反馈 Update P95 / max，ms（276 帧/组） | 42.335 / 166.942 | 33.301 / 130.274 |
| 进程 peak RSS 中位 / max，KiB（3 次/组） | 690196 / 693268 | 688896 / 691180 |

六个进程的规则结果一致：手牌 7、能量 7、双敌 HP 294/12、回合 1、已回放清空事件。生命周期检查仅覆盖 OnDestroy 后不再调度。9 个提交的 P95 等于 max，不能单凭该尾点宣称改善。主流程中位只降 1.46%，另外的快照微测中位变化 −4.25% 至 +1.21%，P95 反而 +15.64% 至 +31.15%。其余两个保留完整图的布局也未过：FIFO 双数组 P95 269.599 vs 215.549 ms，键值对平铺 241.193 vs 226.444 ms（各臂 36 次，分开的对照批次）。无理由将任何变体推广到产品，或减少核心事务覆盖。
